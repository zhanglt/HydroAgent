# HydroAgent 项目需求规格说明书

## 1. 文档定位与基线

本说明书面向研发交接与维护，从当前代码反向提取功能、业务约束和可验证的验收条件。它描述现有系统，不是未来产品承诺，也不将 README 中的功能名称直接视为已通过验收。

- 分析日期：2026-11-19；基准提交：`6afbde4`。
- 基线范围：当前工作区，包含尚未提交的多 LLM/Embedding 配置适配、设置页类型与显示调整、对应测试和说明文档。
- 证据顺序：当前源码、测试中的断言、已有说明文档。测试存在不等于本次已执行；验证状态见[文档索引](README.md)。
- 配套文档：[概要设计](项目概要设计说明书.md)、[详细设计](项目详细设计说明书.md)。

状态术语：**已实现**表示存在可追踪代码；**模拟实现**表示数据或设备动作由软件模拟；**降级实现**表示异常或样本不足时使用替代路径；**仅配置支持**表示可构造配置但未验证真实环境；**未验证**表示缺少当前运行证据；**规则与实现差异**表示代码与项目规则不一致。

## 2. 产品目标、边界与用户

系统以农业分区为基本决策单位，连接数据观察、预测分析、灌溉建议、正式计划、审批、执行状态和审计。自然语言交互用于解释和工具编排，灌溉服务负责最终业务状态判断。

当前软件具备业务闭环，但传感器源是模拟数据，灌溉执行主要表现为数据库状态与日志变化。未发现可据此认定已完成真实阀门、泵站、PLC 或现场传感器联调的驱动链路。天气、LLM、Embedding 是外部依赖，服务启动不代表这些依赖已健康。

### 2.1 用户角色

角色定义以 [rbac_service.py](../src/services/rbac_service.py) 的 `ROLE_MATRIX` 为准。

| 角色 | 主要职责 | 重要权限边界 |
| --- | --- | --- |
| admin 管理员 | 配置、账号、资产、业务和审计管理 | 拥有全部已定义权限 |
| manager 运营经理 | 计划审批执行、知识和资产管理、告警处理、报表导出 | 可查看设置，默认不能管理设置或用户 |
| operator 值班操作员 | 生成与执行计划、处理告警 | HTTP 计划接口允许生成、执行，不授予 `plans:approve` |
| viewer 观察员 | 查询总览、资产、历史、知识、报表和对话 | 不授予计划变更权限；聊天工具权限差异见第 6 节 |
| auditor 审计员 | 历史审计和报表导出 | 默认仅历史与报表相关权限，不等同 Agent 的 auditor 模式 |

角色和 Agent 模式是两套概念。前端菜单隐藏不能替代后端鉴权。接口采用独立权限组合，有页面权限不保证其依赖的全部接口均可访问。

### 2.2 外部系统与数据

| 外部对象 | 现有交互 | 边界 |
| --- | --- | --- |
| Open-Meteo | 城市解析、每日天气预报 | 天气不可用会阻断计划执行，不能用健康检查代替验证 |
| OpenAI 兼容 / MiniMax | 对话、工具调用、参数辅助归一化 | 模型存在性、账号权限、第三方兼容性需独立验证 |
| Ollama / OpenAI Embeddings | 知识文档与查询向量化 | 切换向量空间不自动重建历史向量 |
| 关系数据库 | 业务资产、计划、审批、日志等 | 默认 SQLite，PostgreSQL/MySQL 有连接配置分支 |
| 真实灌溉设备 | 代码预留和模拟控制 | 未实现可证明的现场协议闭环 |

## 4. 关键业务规则与用例

### 4.1 规则矩阵

| 编号 | 规则 | 当前实现与验收边界 |
| --- | --- | --- |
| BR-001 | 每个计划只属于一个分区，start 必须审批 | `IrrigationPlan.zone_id`；所有 start 候选均 requires_approval=true，不仅中高风险 |
| BR-002 | 分区阈值优先，紧急带为阈值减 15 个百分点且不小于 0 | 分区非零值优先，否则数据库默认，再 40；历史 YAML 初始化可使全局默认变成 30，不能声称所有环境默认 40 |
| BR-003 | 降雨风险通常阻止启动，当前湿度进入紧急带可例外 | 实现用前两个日预报的中文描述是否含“雨”；不是严格滚动 48 小时逐小时概率判断 |
| BR-004 | 数据无效、执行器未知/禁用/运行中阻断启动 | 有效湿度范围 0..100；全部采集失败才 missing；无绑定可能回退到其他传感器或模拟源 |
| BR-005 | 时长与湿度亏缺相关 | 无亏缺初始时长 0；有亏缺取 max(默认时长, int(亏缺×1.5)+10)；有效决策树建议且置信度≥0.6可覆盖时长 |
| BR-006 | 拒绝、完成或失效的计划不能重新执行 | 运行中的重复执行直接返回现状；没有数据库级并发单次执行锁证明 |
| BR-007 | hold/defer 不需批准，但需审计 | 当前生成路径主要返回 hold suggestion，记录 LangGraph decision，不新增正式计划行 |
| BR-008 | 自动化不能代替人的启动批准 | auto_check 生成计划或建议；聊天 operator 仍可调用审批工具，用户身份约束缺口见第 6 节 |
| BR-009 | 停止按计划时间或湿度阈值 | 湿度停止保护时间 min(60秒, 计划时长秒数)；状态读取可触发核对与停止，不能据此保证无人轮询时准点停止 |

### 4.2 核心用例

**UC-01 常规灌溉**：操作员选择启用分区 → 生成计划 → 若返回 suggestion 则展示原因并结束 → 若返回待审批计划则由有审批权限的人批准 → 有执行权限的人执行 → 执行前重新校验证据 → 运行状态或停止操作更新日志与计划终态。任一步失败都应显示实际错误，不将“已生成”误报为“已执行”。

**UC-02 有雨且非紧急**：有效湿度低于阈值但未低于紧急带，日预报含雨 → 返回 hold 建议、风险与证据 → 不生成 start 正式计划 → 建议进入审计。天气不可用也应暂缓，不能视为无雨。

**UC-03 计划替换与重复操作**：已有 pending_approval/approved 计划 → 默认生成返回原计划 → 显式 replace 才生成新计划并使旧计划失效；executing 不允许替换。已拒绝计划必须重新生成，不能重新批准后执行旧计划。

**UC-04 知识检索回答**：管理者提交文本 → 切片与向量写入成功 → 用户提问 → 工具检索片段与来源 → LLM 组织回答。Embedding 故障、空库和未配置模型必须与“没有相关知识”区别展示；当前未对所有上游异常统一转换为业务错误。

## 5. 非功能与验收要求

| 编号 | 关注点 | 现状与验收方法 |
| --- | --- | --- |
| NFR-SEC-001 | 认证与权限 | 密码 PBKDF2-HMAC-SHA256，令牌 HMAC 签名；检查 401/403、Cookie 和 API 权限；尚不能认定聊天与多用户数据隔离完整 |
| NFR-SAFE-001 | 可控执行 | 检查计划状态、审批和现场证据；现有顺序状态校验不能证明并发请求或真实设备故障下的单次执行 |
| NFR-TRACE-001 | 可追踪 | 计划保存证据、安全审查、时间和关联 ID；审计 actor 需区分客户端参数与服务端登录身份 |
| NFR-REL-001 | 故障可辨识 | 天气 stale/unavailable、预测 fallback、聚合 errors、SSE error；健康检查只验证应用可响应 |
| NFR-PERF-001 | 页面与外部依赖隔离 | 5 秒传感器缓存、600 秒有效天气缓存、并发同城市请求合并；既有性能结果仅适用于记录中的环境 |
| NFR-DATA-001 | 持久化与恢复 | SQL、LangGraph SQLite、Chroma 和计划文件均需备份；现有 Compose 挂载不足以保证全部业务数据在重建后保留 |
| NFR-MAINT-001 | 配置与可测试性 | 模型和业务设置来源分离；提供测试与源代码追踪；前端 lint/typecheck/build 是独立检查 |
| NFR-COMPAT-001 | 服务兼容 | 旧平铺模型配置与新分组配置兼容；Ollam 别名支持；数据库驱动、LLM 协议兼容以实际部署验证为准 |

不设置无依据的吞吐量、SLA、节水率、预测准确率、最大农场规模或恢复时间承诺。已有[性能分析](performance-analysis.md)和[优化结果](performance-optimization-results.md)作为历史证据引用。

## 6. 已知差异与未完成能力

| 标识 | 证据与影响 | 状态 |
| --- | --- | --- |
| GAP-01 | `AGENTS.md` 要求手动覆盖同一事务创建批准；`manual_override_control` 调用的持久化、批准、执行函数各自提交，后段失败可留存前段结果 | 规则与实现差异 |
| GAP-02 | `POST /api/chat` 仅要求 chat:view，模式允许用户指定或从文本推断；工具选择未绑定当前用户的 plans:* 权限；MCP 直接调用业务服务 | 权限边界缺口，未做运行攻击验证 |
| GAP-03 | 会话列表/读取/删除仅检查 chat:view，持久化未定义用户所有权过滤；不能描述为多租户隔离 | 已实现范围限制 |
| GAP-04 | 计划 actor 由请求体传入，而 AuditEvent 使用登录用户名；两者可能不同，不能将全部 actor 字段都描述为可信身份 | 审计语义差异 |
| GAP-05 | advisor 提示词声明只读，但模式工具白名单包含可 enable/disable/set_threshold 的 manage_alarm | 规则与实现差异 |
| GAP-06 | 默认 40% 是项目规则和模型默认；Config 历史回填默认 30%，初始化 SystemSettings 使用该值；显式新建分区默认仍为 40% | 配置优先级差异 |
| GAP-07 | 无绑定传感器可回退到全局设备/模拟数据；不能将“没有分区传感器绑定”简单等同 missing | 感知边界 |
| GAP-08 | 顺序检查和返回现状不等于事务级互斥；数据库未定义“每区一个活跃计划”的唯一约束，未见锁定执行器的并发保证 | 并发未验证 |
| GAP-09 | 日预报前两条含雨判断近似 48 小时；执行前复核使用有 TTL 的证据，并非每次强制向外部重新请求 | 时间语义边界 |
| GAP-10 | 启动会执行 SQLite 补字段和删除旧会话表；Compose 缺少数据库、工作区和 Skill 持久卷，容器镜像只复制 src，不能假定本地 Skill 文件已打包 | 部署与迁移限制 |

这些差异供后续修复任务使用，本次文档生成不修改系统行为。进一步的硬件集成、统一授权、事务与并发控制、自动迁移和向量重建流程均应独立立项与验证。

## 7. 需求验收组织

按身份权限、资产感知、计划生命周期、聊天知识、运营配置五组验收；优先使用临时数据库与模拟外部请求。核心反例包括：未批准执行、有雨非紧急、传感器无效、执行器运行中、拒绝后执行、已完成重复执行、非法 provider、未知会话和模型服务不可达。

现有测试清单、实际覆盖和未覆盖的区别见[详细设计第 10 节](项目详细设计说明书.md#10-需求设计实现与测试追踪)。本次文档校验记录见[文档索引](README.md)。
